# MarkTrace MVP — implementation contract

Single source of truth for all components. If code and this file disagree, this file wins.
Domain background: `docs/` (case 16). Where `docs/12-erd.md` / `docs/13-data-dictionary.md`
are heavier than this file, this file is the agreed MVP simplification.

## 0. Layout

```
marktrace/
  docker-compose.yml        # db, mock, backend, web
  Makefile                  # gen, up, down, test, verify
  backend/                  # Go module "marktrace/backend": REST API, rules, import, reports
  mock/                     # Go module "marktrace/mock": POST /cz/verify
  tools/gen/                # Go module "marktrace/gen": synthetic T1 + golden generator
  web/                      # React + TypeScript + Vite, served by nginx, proxies /api
  data/C16/T1/              # items.csv codes.csv operations.csv (generated, committed)
  data/C16/mock_registry.csv  # codes known to the mock "ЦРПТ" (generated)
  data/C16/demo_codes.csv     # unused registry codes for live demo via the form (generated)
  golden/                   # status_summary.csv violations.csv (generated by tools/gen)
  docs/                     # project documentation for the 4 checkpoints (see README «Документация»)
```

Stack: Go 1.23+ (`net/http` with Go 1.22 routing patterns, `pgx/v5`, `bcrypt`), PostgreSQL 16,
React 18 + TypeScript + Vite, nginx. Everything starts with `docker compose up --build`;
web UI on http://localhost:8080, backend on :8081 (internal :8080), mock on :8082.

## 1. Rules (rules_version = `2026.11-1`)

### 1.1 GTIN
- Digits only, length 13 or 14, GS1 mod-10 check digit (weights 3,1,3,... from the right,
  excluding the check digit). Stored as string, leading zeros preserved.
- Normalised form for comparison: GTIN-13 → `"0" + gtin13`; GTIN-14 as is. Normalisation is
  only used for comparison, never written back.
- Non-digit chars or wrong length → `GTIN_FORMAT`; bad check digit → `GTIN_CHECKSUM`.

### 1.2 Code mask
`^01(\d{14})21([A-Za-z0-9]{6})$` — exactly 24 chars: `01` + GTIN-14 + `21` + 6-char serial.
Group 1 is the GTIN embedded in the code. Mask failure → `CODE_FORMAT`. The embedded GTIN's
check digit is NOT validated separately (it is compared with the item's GTIN instead).
No trimming or case-folding of any identifier anywhere.

### 1.3 Time
Input: RFC 3339 with mandatory offset (`2026-10-01T09:00:00+03:00` or `...Z`), seconds
precision (fractional seconds rejected). Unparseable / no offset → `TIME_FORMAT`.
Stored as `timestamptz`; output always UTC `2006-01-02T15:04:05Z`.

### 1.4 Lifecycle

| op_type | allowed from status | new status |
|---|---|---|
| issue | code has no accepted history | issued |
| introduce | issued | introduced |
| sell | introduced, returned | sold |
| return | sold | returned |
| dispose | introduced, sold, returned | disposed |

`disposed` is final. Wrong transition → `TRANSITION_NOT_ALLOWED`.
Time: op ts must be strictly greater than ts of the last accepted op of that code, else
`TIME_REVERSED` (equal ts with different content is caught earlier as `IDEMPOTENCY_CONFLICT`
via the (code, ts) key — see 2.3).

### 1.5 Reason codes (stable, machine-readable)
`AUTH_DENIED, REQUIRED_FIELD, VALUE_FORMAT, CODE_FORMAT, GTIN_FORMAT, GTIN_CHECKSUM,
GTIN_MISMATCH, ITEM_NOT_FOUND, CODE_NOT_FOUND, DUPLICATE_CODE, TRANSITION_NOT_ALLOWED,
TIME_FORMAT, TIME_REVERSED, IDEMPOTENCY_CONFLICT, SNAPSHOT_MISMATCH, MOCK_INVALID,
MOCK_UNAVAILABLE`.
Every violation also stores a human-readable Russian `message`.
**Exactly one reason per rejected row/attempt: the first failing check in the order below wins.**

## 2. CSV import

### 2.1 Formats
UTF-8, comma separator, header row required, RFC 4180 quoting (`encoding/csv`).
- `items.csv`: `item_code,name,gtin`
- `codes.csv`: `code,item_code,status,ts` — binds code → item and states the **expected final
  snapshot** of that code after operations are applied.
- `operations.csv`: `op_id,code,op_type,ts,actor`

Header must match exactly (same columns, same order); otherwise the whole session gets
`structure_rejected` with `failure_reason`, no rows are processed. Row with wrong column count →
row rejected `VALUE_FORMAT`.

### 2.2 Session
One import session = any non-empty subset of the three files uploaded together
(`POST /api/imports`, multipart fields `items`, `codes`, `operations`). Processing order is
always items → codes → operations → snapshot check. Rows are processed **in file order**
(never sorted). Each row is processed in its own DB transaction. Each row gets
`processing_status ∈ {accepted, duplicate, rejected}`. Session status:
`running → completed | structure_rejected | failed`. Allowed roles: A1, A3, admin.

### 2.3 Row checks (in this order; first failure wins)

**items.csv** (key `item_code`)
1. empty `item_code`/`name`/`gtin` → `REQUIRED_FIELD`
2. item_code already in `items`: identical (name, gtin) → `duplicate`; different → `IDEMPOTENCY_CONFLICT`.
   Not in `items` but an earlier rejected import row of entity items with same key and identical
   raw content exists → `duplicate` (no new violation).
3. `GTIN_FORMAT` 4. `GTIN_CHECKSUM` 5. accept → insert `items`.

**codes.csv** (key `code`) — accepted rows go to table `code_registry(code, item_code, expected_status, expected_ts)`
1. empty field → `REQUIRED_FIELD`
2. code already in `code_registry`: identical row → `duplicate`; different → `DUPLICATE_CODE`.
   Earlier rejected identical raw row → `duplicate`.
3. `CODE_FORMAT` 4. status not in CodeStatus → `VALUE_FORMAT` 5. `TIME_FORMAT`
6. item_code not in `items` → `ITEM_NOT_FOUND`
7. normalised item GTIN ≠ GTIN embedded in code → `GTIN_MISMATCH`
8. accept → insert `code_registry`.

**operations.csv** (key `op_id`)
1. empty `op_id`/`code`/`op_type`/`ts`/`actor` → `REQUIRED_FIELD`
2. op_id already in `operations` (accepted): identical (code, op_type, ts-as-UTC-instant, actor)
   → `duplicate`; different → `IDEMPOTENCY_CONFLICT`. Earlier rejected attempt with same op_id
   and identical raw content → `duplicate` (no new violation).
3. op_type not in OperationType → `VALUE_FORMAT`
4. `TIME_FORMAT`
5. `CODE_FORMAT`
6. accepted op with same (code, ts) exists: identical (op_type, actor) → `duplicate`, else `IDEMPOTENCY_CONFLICT`
7. existence: for `issue` — code not in `code_registry` → `CODE_NOT_FOUND`; for other types —
   code has no accepted history (not in `codes`) → `CODE_NOT_FOUND`
8. `issue` on code already in `codes` → `DUPLICATE_CODE`
9. `TRANSITION_NOT_ALLOWED`
10. `TIME_REVERSED`
11. accept: insert `operations`, upsert `codes(code, item_code, status, ts, last_actor)`
    (item_code from `code_registry` for issue) — same transaction, row lock on the code.

**Snapshot check** (after operations of a session that included codes.csv or operations.csv):
for every `code_registry` row: actual = `codes` row (or "absent"). If actual status ≠
expected_status or actual ts ≠ expected_ts → violation `SNAPSHOT_MISMATCH` (source `codes`,
ref = code), unless an identical open SNAPSHOT_MISMATCH for that code with the same
expected/actual already exists. Message states expected vs actual.

### 2.4 Idempotency guarantee (KPI K3)
Re-importing the same three T1 files: every row → `duplicate`, 0 new rows in items /
code_registry / codes / operations / violations.

## 3. Operation form (UC1–UC4)
`POST /api/operations {op_type, code, item_code?, ts?, actor?, op_id?}`
- `op_id` defaults to a new UUID; `ts` defaults to now (server); `actor` defaults to username.
- Role check first: issue/introduce → A1; sell/return/dispose → A2; admin → all. Otherwise
  403 + reason `AUTH_DENIED` (attempt is not recorded as an operation attempt).
- For `issue`, `item_code` is required (`REQUIRED_FIELD`); the form creates/validates the
  binding: item must exist (`ITEM_NOT_FOUND`), GTIN must match (`GTIN_MISMATCH`); if the code is
  already in `code_registry` with a different item → `DUPLICATE_CODE`; binding inserted into
  `code_registry` (expected_status/expected_ts = NULL for form-created bindings; NULLs are
  skipped by the snapshot check) in the same transaction as the operation.
- Same checks as 2.3 operations (steps 1–10), then the mock is called
  (`POST {MOCK_URL}/cz/verify {code, gtin}` where gtin = item GTIN, timeout 2 s):
  `is_valid=false` → `MOCK_INVALID` (message includes mock `reason`);
  timeout / network error / non-200 / missing `is_valid` → `MOCK_UNAVAILABLE`.
  Then the write transaction re-checks state under `SELECT … FOR UPDATE`.
- Response: `{attempt_id, op_id, decision: "accepted"|"rejected"|"duplicate", reason?, message?, code?: CodeRow}`.

## 4. Data model (PostgreSQL, migrations embedded in backend, applied on start)
- `users(username pk, password_hash, role ∈ {A1,A2,A3,A4,admin}, display_name)`
  seeded: `prod/prod` A1 «Оператор производства», `retail/retail` A2 «Оператор розницы»,
  `qc/qc` A3 «Контролёр качества», `auditor/auditor` A4 «Аудитор», `admin/admin` admin.
- `sessions(token pk, username, expires_at)` — HttpOnly cookie `mt_session`, SameSite=Lax, 12 h.
- `items(item_code pk, name, gtin)`
- `code_registry(code pk, item_code fk, expected_status null, expected_ts null)`
- `codes(code pk fk code_registry, item_code, status, ts, last_actor)` — projection of last accepted op.
- `operations(op_id pk, code fk, op_type, ts, actor, attempt_id, created_at, unique(code, ts))`
- `import_sessions(session_id uuid pk, started_by, role, started_at, finished_at, status, failure_reason, files jsonb, counters jsonb, rows_created)`
- `import_rows(row_id uuid pk, session_id fk, entity ∈ {items,codes,operations}, line_no, key, raw jsonb, processing_status, reason null)`
- `operation_attempts(attempt_id uuid pk, source ∈ {form,import}, import_row_id null, op_id, code, op_type, ts_raw, actor, initiator, role, decision, reason null, mock_result jsonb null, rules_version, created_at)`
  — one row per operation attempt from the form and per operations.csv row
  (duplicates included, decision = duplicate).
- `violations(violation_id uuid pk, source ∈ {items,codes,operations}, ref, code null, item_code null, reason, message, attempt_id null, import_row_id null, rules_version, created_at, op_ts null, actor null)`
- `violation_resolutions(id uuid pk, violation_id fk, action ∈ {comment, close}, comment not empty, author, created_at)`
  — only A3/admin; second `close` → 409.

Only the backend writes; rules live in one Go package (`backend/internal/rules`) used by both
import and form paths.

## 5. KPI
- **K1** = accepted / (accepted + rejected) over `operation_attempts` (duplicates excluded) × 100, 2 decimals.
- **K2** = codes whose `codes.status` equals the status recomputed by replaying `operations`
  ordered by ts / total codes × 100.
- **K3** = new rows created by the last import session that was a full re-import (report
  `rows_created` per session; UI shows it).
- **K4** = server-side duration (ms) of the last status report query.
- **K5** = golden match percentage (see `/api/golden/compare`).

## 7. Golden files (produced by tools/gen, compared by `/api/golden/compare` and `make verify`)
State to compare: fresh DB + one import session with all three T1 files.
- `golden/status_summary.csv`: header `status,count`, 5 rows in order issued, introduced, sold, returned, disposed (zeros included).
- `golden/violations.csv`: header `code,reason,source,ref`. One row per violation.
  `code` = code (empty for items), `source` ∈ items/codes/operations, `ref` = item_code (items),
  code (codes), op_id (operations). Sort: source order items < codes < operations, then ref,
  then reason (byte order). Values are raw strings from the file.

## 8. Mock `/cz/verify` (service `mock`)
- `POST /cz/verify {code, gtin?}` → 200 `{is_valid: bool, reason?: string}`.
  Order: mask fail → `{false,"INVALID_FORMAT"}`; code not in registry → `{false,"UNKNOWN_CODE"}`;
  gtin given and normalised gtin ≠ GTIN embedded in code → `{false,"GTIN_MISMATCH"}`; else `{true}`.
- Registry: `REGISTRY_FILE` (default `/data/mock_registry.csv`, header `code`).
- Mode via env `MOCK_MODE` and runtime `POST /admin/mode {mode}` / `GET /admin/mode`:
  `normal` | `slow` (sleeps 5 s → backend timeout) | `error` (HTTP 500) | `garbage` (200 with `{}`).
- Idempotent and stateless; `GET /healthz`.

## 9. Generator (tools/gen) — `go run . -seed 16 -out ../../`
Deterministic. Writes T1, mock registry, demo codes, golden. Must be **independent of backend
code** (own GTIN/mask helpers): golden is derived from what the generator injected by
construction, not by running the backend rules.
Sizes: items 80–120, codes rows 500–800, operations rows 600–900. ~20% of items use GTIN-13.
Valid operations written sorted by ts; injected bad rows appended at the end in a fixed order.
Injected errors (each must fail with exactly this reason under §2.3 ordering):
- items: 2× `GTIN_CHECKSUM`, 1× `GTIN_FORMAT` (no codes reference them)
- codes: 2× `CODE_FORMAT`, 2× `DUPLICATE_CODE` (repeat of a valid code with another item),
  1× `GTIN_MISMATCH`, 1× `ITEM_NOT_FOUND` (no operations for the rejected ones),
  2× `SNAPSHOT_MISMATCH` (valid code row whose expected status is deliberately wrong)
- operations (exactly 7 rejected → K1 ≈ 99.1%): sell after only issue → `TRANSITION_NOT_ALLOWED`;
  second dispose → `TRANSITION_NOT_ALLOWED`; second sell after sell → `TRANSITION_NOT_ALLOWED`;
  sell on introduced code with ts earlier than its introduce → `TIME_REVERSED`;
  op on unknown well-formed code → `CODE_NOT_FOUND`; op_type `transfer` → `VALUE_FORMAT`;
  existing op_id with different content → `IDEMPOTENCY_CONFLICT`
- plus 1 exact duplicate operation row (→ `duplicate`, not a violation).
`mock_registry.csv` = all valid T1 codes + the 30 codes from `demo_codes.csv`
(`code,item_code`, items valid, codes unused in T1).

## 10. UI (Russian, React)
Login → top nav by role. Pages: «Операция» (form; op_type select, code, item_code for issue,
ts default now; shows decision + reason; hidden for A3/A4), «Коды» (status report: counters,
filters status/item/actor/period/search, table, «Экспорт CSV»), «Код» (history: binding,
operations timeline, attempts, violations), «Расхождения» (filters, counts by reason, table,
comment/close for A3, «Экспорт CSV»), «Импорт» (3 file inputs, result counters, sessions list,
session detail with rejected rows), «Сводка KPI» (K1–K5 tiles, golden compare with diff),
«Проверка кода» (mock check). Auditor sees everything read-only (no write buttons).
