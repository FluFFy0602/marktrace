# MarkTrace — учёт жизненного цикла кодов маркировки (кейс 16)

MarkTrace — учебный MVP системы прослеживаемости кодов маркировки в духе «Честного знака».
Система принимает операции с кодами (эмиссия, ввод в оборот, продажа, возврат, списание)
через форму и через CSV-импорт. Каждую операцию она проверяет по единым правилам и сверяет
с имитацией ЦРПТ (mock). Отклонённые операции попадают в журнал расхождений с машинно-читаемой
причиной. Ещё есть отчёты по статусам, история каждого кода и KPI.

Обязательный контракт между компонентами — [SPEC.md](SPEC.md). Аналитика кейса лежит в [docs/](docs/),
перечень по защитам — в разделе [«Документация»](#документация).

| Компонент | Технологии | Адрес |
|---|---|---|
| `web` | React 18 + TypeScript + Vite, nginx (раздаёт SPA, проксирует `/api`) | http://localhost:8080 |
| `backend` | Go 1.23+, `net/http`, pgx v5, bcrypt | http://localhost:8081/api |
| `mock` | Go, имитация ЦРПТ `POST /cz/verify` | http://localhost:8082 |
| `db` | PostgreSQL 16 (порт наружу не публикуется) | — |

## Быстрый старт

Нужны Docker с Compose v2, `make`, `curl` и `jq` (без `jq` скрипты переходят на `python3`).

```bash
make up            # docker compose up -d --build
open http://localhost:8080
```

Данные T1 и эталоны уже лежат в репозитории. `make gen` пересоздаёт их (seed 16) и даёт
побайтно те же файлы. Для этого нужен Go.

Демо-пользователи (пароль совпадает с логином; на странице входа есть кнопки быстрого входа):

| Логин | Роль | Кто | Что может |
|---|---|---|---|
| `prod` | A1 | Оператор производства | issue, introduce; импорт |
| `retail` | A2 | Оператор розницы | sell, return, dispose |
| `qc` | A3 | Контролёр качества | импорт; комментарии и закрытие расхождений |
| `auditor` | A4 | Аудитор | только чтение |
| `admin` | admin | Администратор | всё |

Остальные команды:

| Команда | Что делает |
|---|---|
| `make down` | остановить стек, данные сохраняются |
| `make reset` | остановить стек и удалить том БД (`down -v`) |

| `make logs` | логи всех сервисов |

## Правила (rules_version `2026.11-1`)

Все правила находятся в одном пакете `backend/internal/rules`. Им пользуются и импорт, и форма.
Идентификаторы не обрезаются по пробелам и не меняют регистр.

**GTIN.** Только цифры, длина 13 или 14, контрольная цифра GS1 mod-10 (веса 3,1,3,… справа,
без контрольной цифры). Хранится строкой как есть, ведущие нули сохраняются.
- Не цифры или неверная длина → `GTIN_FORMAT`; неверная контрольная цифра → `GTIN_CHECKSUM`.
- **Политика GTIN-13:** для сравнения GTIN-13 приводится к GTIN-14 ведущим нулём
  (`4601234567893` → `04601234567893`). Нормализованная форма только сравнивается и никуда
  не записывается.

**Маска кода маркировки:** `^01(\d{14})21([A-Za-z0-9]{6})$` — ровно 24 символа:
`01` + GTIN-14 + `21` + серийный номер из 6 символов. GTIN внутри кода отдельно по контрольной
цифре не проверяется: его сравнивают с GTIN товара (`GTIN_MISMATCH`). Скобочная запись GS1
`(01)…(21)…` маску не проходит (`CODE_FORMAT`).

**Время:** RFC 3339 с обязательным часовым поясом, с точностью до секунды
(`2026-10-01T09:00:00+03:00` или `…Z`). Доли секунды и время без пояса → `TIME_FORMAT`.
Хранится как `timestamptz`, выводится в UTC `2006-01-02T15:04:05Z`.

**Переходы статусов:**

| Операция | Допустима из статуса | Новый статус |
|---|---|---|
| issue | у кода нет принятой истории | issued |
| introduce | issued | introduced |
| sell | introduced, returned | sold |
| return | sold | returned |
| dispose | introduced, sold, returned | disposed (финальный) |

Неверный переход → `TRANSITION_NOT_ALLOWED`. Время операции должно быть строго позже последней
принятой операции по этому коду, иначе → `TIME_REVERSED`.

**Порядок проверок строки operations.csv (первая неудачная проверка определяет причину):**

1. пустое поле → `REQUIRED_FIELD` (неверное число колонок → `VALUE_FORMAT`)
2. `op_id` уже принят: то же содержимое → `duplicate`, другое → `IDEMPOTENCY_CONFLICT`;
   ранее отклонённая идентичная строка → `duplicate` без нового нарушения
3. неизвестный `op_type` → `VALUE_FORMAT`
4. время → `TIME_FORMAT`
5. маска кода → `CODE_FORMAT`
6. уже есть принятая операция с тем же (code, ts): то же содержимое → `duplicate`,
   иначе `IDEMPOTENCY_CONFLICT`
7. код неизвестен (`issue` — нет в реестре кодов, остальные — нет принятой истории) → `CODE_NOT_FOUND`
8. `issue` по коду, у которого уже есть история → `DUPLICATE_CODE`
9. переход → `TRANSITION_NOT_ALLOWED`
10. время назад → `TIME_REVERSED`
11. приём: запись в `operations` и обновление `codes` в одной транзакции под блокировкой кода

Порядок для items.csv: `REQUIRED_FIELD` → повтор/`IDEMPOTENCY_CONFLICT` → `GTIN_FORMAT` → `GTIN_CHECKSUM`.
Для codes.csv: `REQUIRED_FIELD` → повтор/`DUPLICATE_CODE` → `CODE_FORMAT` → статус (`VALUE_FORMAT`)
→ `TIME_FORMAT` → `ITEM_NOT_FOUND` → `GTIN_MISMATCH`. После операций идёт сверка снимка:
codes.csv задаёт ожидаемый итоговый статус и время каждого кода. Каждое расхождение с фактом
даёт `SNAPSHOT_MISMATCH`.

**Форма** (`POST /api/operations`) делает следующее:
1. Сначала проверяет роль: issue/introduce — A1, sell/return/dispose — A2, admin — всё.
   Иначе 403 `AUTH_DENIED`, и попытка не записывается.
2. Для `issue` проверяет и создаёт привязку кода к товару: `REQUIRED_FIELD` (нет товара),
   `ITEM_NOT_FOUND`, `GTIN_MISMATCH`, `DUPLICATE_CODE`.
3. Выполняет проверки 1–10.
4. Вызывает mock (таймаут 2 с): `is_valid=false` → `MOCK_INVALID`;
   таймаут, сетевая ошибка, не-200 или ответ без `is_valid` → `MOCK_UNAVAILABLE`.
5. Повторно проверяет состояние под `SELECT … FOR UPDATE` и записывает результат.

**Коды причин:** `AUTH_DENIED, REQUIRED_FIELD, VALUE_FORMAT, CODE_FORMAT, GTIN_FORMAT,
GTIN_CHECKSUM, GTIN_MISMATCH, ITEM_NOT_FOUND, CODE_NOT_FOUND, DUPLICATE_CODE,
TRANSITION_NOT_ALLOWED, TIME_FORMAT, TIME_REVERSED, IDEMPOTENCY_CONFLICT, SNAPSHOT_MISMATCH,
MOCK_INVALID, MOCK_UNAVAILABLE`. У каждой отклонённой строки или попытки ровно одна причина
и сообщение на русском.

## Допущения и отличия от логической модели ERD v1.0 (docs/12-erd.md §9)

`docs/12-erd.md` и `docs/13-data-dictionary.md` версии 2.0 уже описывают реализованную схему.
Ниже — чем она отличается от первой логической модели (v1.0), построенной до реализации.

- **Упрощённая модель.** Таблицы `operation_requests` и `verification_checks` из ERD
  объединены в `operation_attempts`: одна строка на каждую попытку из формы и каждую строку
  operations.csv, а ответ мока хранится в поле `mock_result jsonb`. Привязка «код → товар»
  и ожидаемый снимок из codes.csv вынесены в `code_registry`. Таблица `codes` содержит только
  проекцию последней принятой операции.
- **Синхронный mock.** Форма вызывает ЦРПТ синхронно. Состояния `pending` и отложенной
  перепроверки нет: недоступность mock сразу даёт отказ `MOCK_UNAVAILABLE`, и операцию можно
  повторить с тем же `op_id`. CSV-импорт mock не вызывает: при импорте коды проверяются по
  реестру кодов из codes.csv.
- **Импорт синхронный.** Запрос длится, пока обрабатываются все строки (T1 — 3–5 с). Каждая
  строка обрабатывается в своей транзакции.
- **Время по умолчанию.** Если `ts` не задан, форма берёт текущее время сервера с точностью
  до секунды. Две операции по одному коду в одну и ту же секунду столкнутся по ключу
  (code, ts) → `IDEMPOTENCY_CONFLICT`. Поэтому `make demo` передаёт время явно.
- **Эталон рассчитан на чистую БД.** `/api/golden/compare` и K5 сравнивают текущее состояние
  с golden-файлами. После операций через форму (`make demo`) K5 падает ниже 100% — так и
  должно быть. Чтобы вернуть эталонное состояние: `make verify`.
- K4 хранится в памяти бэкенда: после перезапуска он пуст, пока кто-нибудь не откроет «Коды».

## Сверка с эталоном

```bash
make verify
```

Команда пересоздаёт стек с пустой БД и входит как `qc`. Затем импортирует три файла T1 и
проверяет, что `/api/golden/compare` даёт 100% по `status_summary.csv` и `violations.csv`,
а K1 ≥ 99 и K2 = 100. После этого импортирует те же файлы ещё раз: `rows_created = 0`,
новых нарушений нет. В конце проверяет, что аудитор получает 403 на все записи, а nginx
отдаёт SPA, deep link и `/api` с cookie. Эталонные значения:

| Показатель | Значение |
|---|---|
| items: принято / отклонено | 96 / 3 |
| codes: принято / отклонено | 512 / 6 |
| operations: принято / дубль / отклонено | 862 / 1 / 7 |
| status_summary | issued 300, introduced 110, sold 78, returned 12, disposed 12 |
| нарушений | 18 (16 строк + 2 `SNAPSHOT_MISMATCH`) |
| K1 | 99.19% |

Golden-файлы строит генератор `tools/gen` по тому, что он сам внедрил в данные. Код бэкенда
генератор не использует.

## Демонстрация D16

Перед показом: `make verify` (чистое эталонное состояние, K5 = 100%). Для живых операций
берите коды из [data/C16/demo_codes.csv](data/C16/demo_codes.csv): они есть в реестре mock,
но отсутствуют в T1. Каждый код можно провести через `issue` только один раз.

**Через UI (http://localhost:8080):**

1. Войти как `qc`. «Импорт»: выбрать три файла из `data/C16/T1/` → «Импортировать».
   Показать счётчики и сеанс с отклонёнными строками. Повторить импорт: всё `duplicate`,
   «Создано новых строк: 0».
2. «Сводка KPI» → «Сверить с эталоном»: оба файла совпадают, 100%.
3. «Расхождения»: счётчики по причинам, фильтры, комментарий и закрытие расхождения (A3).
4. Выйти и войти как `prod`. «Операция»: `issue` для двух демо-кодов (выбрать товар из
   `demo_codes.csv`), затем `introduce` для обоих.
5. Выйти и войти как `retail`. Сделать `sell` для обоих кодов, затем `return` для одного.
   Повторный `sell` проданного кода → `TRANSITION_NOT_ALLOWED`.
6. «Коды» → открыть код: привязка, лента операций, попытки, нарушения.
7. Включить сбой ЦРПТ:
   `curl -X POST localhost:8082/admin/mode -H 'Content-Type: application/json' -d '{"mode":"error"}'`.
   Операция в форме → `MOCK_UNAVAILABLE`. То же для `"garbage"` (ответ `{}`) и `"slow"`
   (ответ через 5 с, а таймаут бэкенда 2 с). Вернуть `"normal"`, повторить — операция принята.
8. «Проверка кода»: демо-код с чужим GTIN (например `4601234567893`) → `GTIN_MISMATCH`;
   код со скобками → `INVALID_FORMAT`.
9. Войти как `auditor`: кнопок записи нет, всё доступно только для чтения.

**Через API:** `make demo` выполняет шаги 4–8 и проверяет каждый ответ. Скрипт сам берёт два
ещё не использованных демо-кода, поэтому его можно запускать повторно (всего 15 запусков
на 30 кодах).

## KPI

| KPI | Определение | Цель |
|---|---|---|
| K1 | принятые / (принятые + отклонённые) попытки операций × 100; дубли не учитываются | ≥ 99% |
| K2 | доля кодов, у которых `codes.status` совпадает со статусом, пересчитанным по `operations` в порядке ts | 100% |
| K3 | новые строки, созданные последним полным повторным импортом (`rows_created`) | 0 |
| K4 | серверное время последнего запроса отчёта по статусам, мс | ≤ 2000 мс |
| K5 | процент совпадения текущих выгрузок с golden-файлами | 100% |

### Замечания для показа

- Перед показом выполнить `make verify`: стек пересоздаётся с чистой БД, T1 импортируется
  дважды, K1 = 99,19%, K3 = 0, K5 = 100%, все 30 демо-кодов свободны.
- K1 считает и намеренные отказы формы: после сценария D16 (3 отказа) он опускается до
  ≈ 98,9% и плитка становится красной. «Сводку KPI» лучше показать до негативных сценариев.
- K5 = 100% только для состояния «чистая БД + один импорт T1»; любая операция через форму
  или свой CSV меняет выгрузки, и процент совпадения падает — это ожидаемо.
- K3 берётся по последнему полному (три файла) сеансу, содержимое которого совпадает
  (sha256 каждого файла) с более ранним полным сеансом. Импорт другого набора файлов
  повторным импортом не считается.
- Файлы можно загружать и по отдельности в любом порядке: строки, отклонённые только из-за
  отсутствия ещё не загруженного кода (`CODE_NOT_FOUND`) или товара (`ITEM_NOT_FOUND`),
  при повторной загрузке проверяются заново. Надёжнее всего грузить все три файла сразу.
- Голая кавычка внутри поля без кавычек (`Сыр "Х"`) допускается; файл с ней не отклоняется.
- Ограничение: CSV-выгрузки содержат сырые значения из файлов (так требует формат эталона),
  защиты от формул Excel (`=…`, `+…`, `@…`) нет.

### Отличия от SPEC.md

- §2.3, сверка снимка: повторный `SNAPSHOT_MISMATCH` не создаётся, если такое же нарушение
  уже есть — открытое **или закрытое**. Иначе повторный импорт после закрытия расхождения
  контролёром создавал бы новую строку и ломал K3 = 0.
- §2.3, шаг 2 operations и шаг 2 codes: ранее отклонённая идентичная строка считается
  `duplicate`, кроме случаев `CODE_NOT_FOUND` / `ITEM_NOT_FOUND`, когда код или товар
  с тех пор появился, — тогда строка проверяется заново.
- §5, K3: повторным импортом считается только сеанс с тем же содержимым файлов, а не любой
  второй полный сеанс.
