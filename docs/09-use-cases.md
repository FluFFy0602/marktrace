# 09. Use Case и пользовательские сценарии

Акторы — из [реестра](08-actors-registry.md). Диаграмма: [`diagrams/use-case.png`](diagrams/use-case.png). Каждый Use Case описывает цель одного актора и результат, который ценен именно ему. Внутренние проверки системы (формат кода, GTIN, переходы статусов, мок-сервис) в шагах не расписаны: они видны актору только как результат («принято» или «отказано, потому что…»).

Сквозные правила проверки операций:

| Операция | Допустима после статуса | Новый статус |
|---|---|---|
| issue | кода ещё нет | issued |
| introduce | issued | introduced |
| sell | introduced или returned (без активной продажи подряд) | sold |
| return | sold | returned |
| dispose | introduced, sold, returned | disposed (финальный) |

Время любой операции — строго позже последней принятой операции этого кода, иначе отказ `TIME_REVERSED` (`SPEC.md` §1.4).

Примечание к реализации MVP: форма «Операция» оформляет одну операцию над одним кодом. Карточки кода внутри формы нет — после ответа форма показывает решение и новый статус, история открывается на экране «Код». Отличия сценариев от MVP отмечены в карточках ниже и сведены в [18](18-user-stories.md), раздел «Отклонения».

Самостоятельной проверки кода через мок как отдельного сценария нет: это шаг внутри UC1–UC4, а мок-сервис остаётся вторичным актором. В MVP есть вспомогательный экран «Проверка кода» (`POST /api/verify`, US-21): он показывает ответ мока и ничего не сохраняет. Техническая учётная запись `admin` (см. [08](08-actors-registry.md)) может выполнять любой сценарий и в перечне не выделяется.

## UC1. Зарегистрировать выпуск и ввод партии кодов

| Поле | Содержание |
|---|---|
| Актор | Оператор производства. Вторичный: мок-сервис проверки кода |
| Цель | Выпустить партию кодов и ввести принятые коды в оборот |
| Предусловия | Оператор авторизован; товар есть в справочнике, у него указан GTIN |
| Триггер | Партия товара выпущена |
| Основной сценарий | 1. Открывает форму «Выпуск и ввод в оборот» и выбирает товар. 2. Вводит или вставляет список кодов партии. 3. Подтверждает выпуск. 4. Видит результат по каждому коду: принят или отклонён с причиной. 5. Подтверждает ввод принятых кодов в оборот. 6. Получает сводку партии: сколько введено, сколько отклонено |
| Альтернативы и исключения | **А1.** Код уже существует — он отклоняется как дубль, остальные принимаются. **А2.** Неверный формат кода или GTIN — отклонение с названием правила. **А3.** Ввод в оборот раньше выпуска — недоступен. **А4.** Мок-сервис недоступен — операция отклоняется с `MOCK_UNAVAILABLE` и попадает в расхождения; оператор повторяет её с тем же `op_id` |
| Постусловия | Принятые коды в статусе «введён в оборот», у отклонённых записана причина |
| Метрика успеха | Партия из 100 кодов оформляется не более чем за 3 действия; корректных операций не менее 99% |
| Реализация MVP | Форма принимает один код за запрос (шаги 2–5 выполняются для каждого кода). Партия целиком оформляется импортом `operations.csv` (UC7) — метрика «3 действия на партию» достигается так |

## UC2. Продать код

| Поле | Содержание |
|---|---|
| Актор | Оператор склада. Вторичный: мок-сервис проверки кода |
| Цель | Оформить продажу кода или сразу понять, почему она невозможна |
| Предусловия | Оператор авторизован; код введён в оборот |
| Триггер | Отгрузка или продажа товара |
| Основной сценарий | 1. Открывает форму продажи, вводит или сканирует код. 2. Видит карточку кода: товар и текущий статус. 3. Подтверждает продажу. 4. Видит подтверждение со статусом «продан». 5. При необходимости оформляет следующий код |
| Альтернативы и исключения | **А1.** Код не введён в оборот — отказ «продажа до ввода». **А2.** Код уже продан — отказ «повторная продажа без возврата». **А3.** Код выведен из оборота — отказ. **А4.** Неверный формат кода или GTIN — отказ с названием правила |
| Постусловия | Статус кода «продан», операция записана в протокол |
| Метрика успеха | Не более 3 действий на код; все недопустимые продажи отклоняются |
| Реализация MVP | Шага 2 (карточка кода до подтверждения) в форме нет: текущий статус виден на экране «Код» или в ответе после операции |

## UC3. Оформить возврат от покупателя

| Поле | Содержание |
|---|---|
| Актор | Оператор склада. Вторичный: мок-сервис проверки кода |
| Цель | Принять код обратно и дать возможность продать его повторно |
| Предусловия | Оператор авторизован; код в статусе «продан» |
| Триггер | Покупатель вернул товар |
| Основной сценарий | 1. Вводит или сканирует код возвращённого товара. 2. Видит карточку кода: статус «продан» и дату продажи. 3. Выбирает «возврат» и подтверждает. 4. Видит статус «возвращён» и подсказку, что код можно продать повторно |
| Альтернативы и исключения | **А1.** Код не продавался — отказ «возврат без продажи». **А2.** Код выведен из оборота — отказ. **А3.** Время возврата раньше времени продажи — отказ «время раньше последней операции». **А4.** После возврата код продаётся повторно — сценарий UC2 |
| Постусловия | Статус «возвращён», повторная продажа разрешена |
| Метрика успеха | Возврат оформляется не более чем за 3 действия; повторная продажа после возврата проходит без ошибок |
| Реализация MVP | Карточки кода в форме (шаг 2) и подсказки «можно продать повторно» (шаг 4) нет; форма показывает новый статус «возвращён» |

## UC4. Списать код (вывести из оборота)

| Поле | Содержание |
|---|---|
| Актор | Оператор склада. Вторичный: мок-сервис проверки кода |
| Цель | Вывести код из оборота так, чтобы с ним больше нельзя было работать |
| Предусловия | Оператор авторизован; код введён в оборот, продан или возвращён |
| Триггер | Брак, списание или окончание срока годности |
| Основной сценарий | 1. Вводит или сканирует код. 2. Видит карточку кода и текущий статус. 3. Выбирает «вывод из оборота» и подтверждает. 4. Видит статус «выведен» |
| Альтернативы и исключения | **А1.** Код уже выведен — отказ «повторный вывод». **А2.** Код только выпущен и не введён в оборот — отказ. **А3.** Неверный формат или GTIN — отказ с названием правила |
| Постусловия | Статус «выведен» — финальный; любые следующие операции с этим кодом отклоняются |
| Метрика успеха | Все повторные операции над выведенным кодом блокируются |

## UC5. Разобрать расхождения

| Поле | Содержание |
|---|---|
| Актор | Контролёр качества |
| Цель | Найти ошибочные операции, понять причину и закрыть или обосновать каждую |
| Предусловия | Контролёр авторизован; данные загружены |
| Триггер | Конец месяца, плановый аудит, жалоба |
| Основной сценарий | 1. Открывает отчёт «Расхождения». 2. Задаёт период, товар и актора. 3. Выбирает уровень детализации: по коду, по операции или по причине. 4. Видит нарушения с причиной (формат, GTIN, уникальность, последовательность, время). 5. Открывает код и смотрит его историю. 6. Передаёт исправление оператору или проводит корректирующую операцию. 7. Перезапускает проверки и видит обновлённую долю корректных операций |
| Альтернативы и исключения | **А1.** Нарушений нет — отчёт пуст, доля корректных операций 100%. **А2.** Исправление даёт новое нарушение — показана новая причина. **А3.** Код выведен — исправить нельзя, расхождение закрывается с комментарием |
| Постусловия | Расхождения закрыты или обоснованы, показатель доли корректных операций пересчитан |
| Метрика успеха | Доля корректных операций не менее 99%; отчёт совпадает с `violations.csv` |
| Реализация MVP | Шаг 3: отдельного переключателя уровня детализации нет — есть фильтры по причине, источнику, состоянию и счётчики по причинам (C5). Шаг 6: у контролёра нет прав на операции, исправление вносит оператор (A1/A2) новой операцией или повторным импортом. Шаг 7: команды «перезапустить проверки» нет — K1 и отчёт пересчитываются при каждом открытии; перепроверка — повторный импорт исправленного файла (бэклог US-22) |

## UC6. Получить статусы кодов и выгрузить CSV

| Поле | Содержание |
|---|---|
| Актор | Контролёр качества, аудитор (только чтение). Вторичный: учётная система заказчика (принимает файл) |
| Цель | Увидеть, сколько кодов в каком статусе, и получить файл для проверки |
| Предусловия | Актор авторизован; данные есть |
| Триггер | Конец периода, запрос руководителя, аудит |
| Основной сценарий | 1. Открывает отчёт «Статусы кодов». 2. Задаёт период, товар, статус, актора. 3. Видит таблицу и счётчики по статусам. 4. Нажимает «Экспорт CSV». 5. Получает файл с полями `code, item_code, status, last_ts` |
| Альтернативы и исключения | **А1.** По фильтрам нет данных — пустой отчёт с сообщением. **А2.** Аудитор не может изменить данные — операции ему недоступны. **А3.** Отчёт строится дольше 2 с — виден индикатор выполнения |
| Постусловия | Файл получен; на наборе T1 отчёт совпадает с `status_summary.csv` |
| Метрика успеха | Отчёт строится не дольше 2 с; совпадение с эталоном 100% |

## UC7. Загрузить данные из учётной системы

| Поле | Содержание |
|---|---|
| Актор | Контролёр качества; оператор производства (A1) — загрузка выгрузки своей учётной системы. Вторичный: учётная система заказчика (источник файлов) |
| Цель | Загрузить номенклатуру, коды и журнал операций без дублей и увидеть, что отклонено |
| Предусловия | Пользователь (A1 или A3) авторизован; подготовлены от одного до трёх файлов CSV |
| Триггер | Начало периода, получение выгрузки, повторная загрузка после исправлений |
| Основной сценарий | 1. Открывает «Импорт данных» и выбирает файлы (любой непустой набор из трёх). 2. Запускает загрузку. 3. Видит протокол: загружено, пропущено как дубль, отклонено с причинами. 4. Переходит к расхождениям, если есть отклонённые строки |
| Альтернативы и исключения | **А1.** Повторная загрузка того же файла — дубли пропускаются, новых строк 0. **А2.** Часть строк ошибочна — валидные загружаются, ошибочные попадают в «Расхождения». **А3.** Заголовок файла не совпадает с форматом — загрузка отменяется целиком (`structure_rejected`) с указанием файла |
| Постусловия | Данные без дублей, статусы пересчитаны, сессия записана в журнал |
| Метрика успеха | Повторный импорт T1 даёт 0 новых строк |

## Пользовательские сценарии (опыт пользователя)

**Андрей, оператор склада (UC3).** Андрей стоит у возвратного стола с терминалом сбора данных, покупатель ждёт. Он сканирует код и выбирает «возврат». Система отвечает «нельзя вернуть: код не продавался» — он понимает причину и проверяет чек вместе с покупателем. Если бы система написала просто «ошибка», он бы пошёл звонить в поддержку.

**Ирина, контролёр качества (UC5).** В последний рабочий день месяца Ирина готовит сверку за ноутбуком. На прошлом аудите расхождения нашли после проверки, и ей тревожно. Она открывает отчёт расхождений, видит 14 строк с причинами и фильтрует по актору, чтобы понять, где ошибаются чаще. Мешает, что код приходится открывать отдельно, поэтому история кода должна открываться в один клик.

## Чек-лист полноты

- У каждого актора есть Use Case: A1 — UC1, UC7; A2 — UC2–UC4; A3 — UC5–UC7; A4 — UC6; admin — все (техническая роль).
- У каждого Use Case минимум две альтернативы или исключения.
- Результат каждого сценария ценен актору, а не системе.
- Вторичные акторы (мок-сервис, учётная система) отражены там, где участвуют.
