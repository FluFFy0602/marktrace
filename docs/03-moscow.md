# 03. Приоритизация требований MoSCoW

Версия 0.2. Согласуют: аналитик (Завгороднев Ярослав) и тимлид (Шиншин Алексей) с заказчиком. Изменения — через issue `scope-change`.

Принцип: **Must** — то, без чего не работает сквозной сценарий, не считается KPI «доля корректных операций ≥ 99%» либо что прямо названо обязательным в описании кейса и методичке. **Should** — важно, но MVP без этого работает. **Could** — удобства и расширения. **Won't** — сознательно исключено условиями кейса или выходит за рамки макета.

## Must have (14)

| ID | Требование | Основание в кейсе | Критерий приёмки |
|---|---|---|---|
| M1 | Формы операций issue / introduce / sell / return / dispose | Ожидаемые артефакты: формы операций | Операция оформляется, статус кода обновляется |
| M2 | Проверка допустимых переходов по последнему статусу кода | Правила кейса, §2 «Жизненный цикл» | sell без introduce отклоняется с причиной |
| M3 | Проверка формата кода и GTIN (длина, контрольная цифра) | Валидации кейса | Некорректные строки T1 найдены |
| M4 | Уникальность кода, привязка к товару | Валидации кейса | Дубль кода отклонён |
| M5 | Отчёт «Статусы кодов» со счётчиками и экспорт CSV | Требования к отчётности | Совпадение с `golden/status_summary.csv` |
| M6 | Отчёт «Расхождения/ошибки» с причиной | Требования к отчётности | Совпадение с `golden/violations.csv` |
| M7 | Идемпотентный импорт CSV items, codes, operations | НФТ «Надёжность», §5 интеграции | Повторный импорт даёт 0 новых строк |
| M8 | Журнал сессий импорта и протокол отклонений | §5 «журналирование сессий импорта» | Каждая сессия записана, причины отказов видны |
| M9 | Сводка KPI «доля корректных операций» | Бизнес-цель кейса | Значение ≥ 99% на T1 |
| M10 | REST-мок `POST /cz/verify {code, gtin?} → {is_valid, reason?}` | Ожидаемые артефакты: «поднимите мок-проверку кода» | Запрос возвращает результат и причину |
| M11 | Роли доступа, только чтение для аудитора | НФТ «Доступы» | Аудитор не может изменить данные |
| M12 | Данные T1: 500+ кодов, с ошибочными строками | §7 данные | Файлы лежат в `/data` |
| M13 | BPMN процесса, ERD, словарь данных | Обязательные артефакты §7.2 | Модели приложены и согласованы с правилами |
| M14 | README и контрольные примеры | Критерии приёмки кейса | Шаги воспроизводимы |

## Should have (4)

| ID | Требование | Обоснование |
|---|---|---|
| S1 | Фильтры отчётов: период, товар, статус, актор | Требование к отчётности; без фильтров отчёты работают, но менее удобны |
| S2 | UI трекинга кода: история операций | Ожидаемый артефакт, но проверки и отчёты работают без него |
| S3 | Три контролируемых сценария ошибок мока: неверный формат, неизвестный код, несоответствие GTIN | Расширяет M10 |
| S4 | Версионирование правил проверки (версия, дата) | Требование к трассируемости; вручную можно фиксировать в README |

## Сводка

| Категория | Количество |
|---|---|
| Must | 14 |
| Should | 4 |
| Could | 5 |
| Won't | 5 |

Правило: все Must закрываются к v0.1 и v1.0 до начала работ по Could. Ограничение кейса — ≤ 5 пользовательских операций: форма операций (M1), два отчёта (M5, M6), импорт (M7) и экспорт CSV укладываются в этот лимит; остальные Must — проверки, данные, документы и мок — пользовательскими операциями не являются.
