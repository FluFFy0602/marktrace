# 06. Портрет пользователя

Персонажи вымышленные, собраны по ролям кейса (оператор производства, оператор розницы/склада, контролёр качества). Подтвердить интервью с заказчиком.

## Аватар 1 (основной): Ирина, контролёр качества данных

| Поле | Описание |
|---|---|
| Имя, возраст | Ирина Соколова, 34 года |
| Должность | Контролёр качества данных маркировки в сети магазинов косметики (мидл-офис) |
| Кто она | Сверяет данные учёта с выгрузками оператора, ведёт разбор расхождений перед проверками |
| Цели и мотивация | Убедиться, что статусы кодов в учёте верны; закрывать расхождения до претензий оператора; показать руководителю долю корректных операций |
| Боли и фрустрации | Ошибку находят поздно; причину приходится выяснять вручную в Excel; повторная выгрузка создаёт дубли; неясно, кто и когда провёл неверную операцию |
| Что ей нужно от системы | Отчёт «Расхождения» с причиной и актором; фильтры по периоду, товару, статусу; экспорт CSV; перезапуск проверки (в MVP не реализован: перепроверка — повторным импортом, кнопка — бэклог US-22) |
| Где ищет информацию | Внутренний чат, база знаний оператора, вебинары по маркировке, профильные Telegram-каналы |
| Техническая грамотность | Уверенный пользователь Excel и учётной системы, SQL не пишет |
| Критичный сценарий | Конец месяца: сверить журнал операций с реестром статусов |

## Второстепенный пользователь

Оператор производства — регистрирует issue/introduce. Нужен пакетный ввод и защита от дублей кодов. Отдельный аватар не строим: в MVP его сценарии закрываются теми же формами.

## Выводы для продукта

1. Сообщение об ошибке должно называть правило и причину, а не «операция отклонена».
2. Отчёты важнее форм: основная ценность для Ирины — быстрый разбор расхождений.
3. Всё должно работать без УКЭП и боевых данных, на CSV.
