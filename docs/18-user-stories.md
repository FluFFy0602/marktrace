# 18. User Stories

**MarkTrace · версия 1.0 · 16.11.2026**

Практическая работа 3.2 (ПР-6). Источники: персонажи — [06-user-persona.md](06-user-persona.md), роли — [08-actors-registry.md](08-actors-registry.md), сценарии — [09-use-cases.md](09-use-cases.md), приоритеты — [03-moscow.md](03-moscow.md), реализация — `SPEC.md` и код в `backend/`, `web/`. Карта историй — [19-user-story-map.md](19-user-story-map.md), экраны — [22-ui-flow.md](22-ui-flow.md).

Составляет истории аналитик (Завгороднев Ярослав), техническую реализуемость проверяют backend (Брусникин Максим) и frontend (Жраков Артём), приоритеты согласует тимлид (Шиншин Алексей).

## Правила записи

| Поле | Как заполняется |
|---|---|
| ID | `US-NN`, сквозная нумерация |
| История | «Как <роль>, я хочу <действие>, чтобы <ценность>» — без технических деталей |
| Критерии приёмки | Дано / Когда / Тогда; проверяются на демо-пользователях (`prod`, `retail`, `qc`, `auditor`, пароль = логин) и наборе T1 |
| Приоритет | ID требования из MoSCoW (M — Must, S — Should, C — Could) |
| Оценка | Story points по шкале Фибоначчи 1, 2, 3, 5, 8 (относительная трудоёмкость, эталон: US-02 = 2 SP) |
| UC | Сценарий из [09-use-cases.md](09-use-cases.md) |
| Экран / API | Где история реализована в MVP: маршрут веб-интерфейса и метод REST API (`SPEC.md` §6) |
| Реализуемость | Вывод разработчиков: каким модулем закрыта история, ограничения и отклонения от документации |

Роли в историях совпадают с ролями системы: A1 — оператор производства, A2 — оператор розницы/склада, A3 — контролёр качества, A4 — аудитор. Учётная запись `admin` технической роли администратора в историях не участвует.

## Карточки историй

### US-01. Вход и навигация по роли

| Поле | Содержание |
|---|---|
| История | Как сотрудник (A1–A4), я хочу войти под своей учётной записью и сразу видеть только доступные моей роли действия, чтобы не ошибиться разделом |
| Критерии приёмки | **1.** Дано: пользователь не вошёл. Когда: открывает любой адрес системы. Тогда: открывается экран входа, после входа — запрошенная страница. **2.** Дано: введён неверный пароль. Когда: нажимает «Войти». Тогда: вход не выполнен, показана ошибка. **3.** Дано: вошёл `prod` или `retail`. Тогда: стартовый экран «Операция», в верхнем меню есть пункт «Операция». **4.** Дано: вошёл `qc` или `auditor`. Тогда: стартовый экран «Коды», пункта «Операция» нет, прямой переход на `/operation` перенаправляет на «Коды» |
| Приоритет / SP | M11 / 3 |
| UC | Предусловие всех UC1–UC7 |
| Экран / API | Вход (`/login`), верхнее меню; `POST /api/auth/login`, `GET /api/auth/me`, `POST /api/auth/logout` |
| Реализуемость | Реализовано: `backend/internal/auth`, cookie `mt_session` (HttpOnly, 12 ч), пароли bcrypt. Права проверяет backend; скрытие пунктов меню — только удобство |

### US-02. Эмиссия кода

| Поле | Содержание |
|---|---|
| История | Как оператор производства, я хочу зарегистрировать эмиссию кода с привязкой к товару, чтобы код появился в учёте |
| Критерии приёмки | **1.** Дано: вошёл `prod`, код из `data/C16/demo_codes.csv` ещё не использован. Когда: выбирает «Эмиссия», вводит код, выбирает товар из `demo_codes.csv`, нажимает «Отправить». Тогда: решение «Принято», статус кода «Эмитирован». **2.** Дано: товар не выбран. Тогда: форма не отправляется (поле обязательно). **3.** Дано: тот же код уже эмитирован. Когда: повторная эмиссия с другим `op_id`. Тогда: «Отклонено», причина `DUPLICATE_CODE` |
| Приоритет / SP | M1, M4 / 2 |
| UC | UC1 (шаги 1–4) |
| Экран / API | Операция (`/operation`); `GET /api/items`, `POST /api/operations {op_type: "issue", code, item_code}` |
| Реализуемость | Реализовано: `backend/internal/ops` (форма и общий движок правил), привязка кода к товару пишется в `code_registry` в той же транзакции. Перед записью вызывается мок ЦРПТ, поэтому для демо годятся только коды из реестра мока |

### US-04. Отказ с названием правила (производство)

| Поле | Содержание |
|---|---|
| История | Как оператор производства, я хочу, чтобы код с ошибкой формата, неверным GTIN или повтором был отклонён с названием правила, чтобы исправить его до отгрузки |
| Критерии приёмки | **1.** Дано: код короче 24 символов. Когда: отправляет эмиссию. Тогда: `CODE_FORMAT`, сообщение на русском. **2.** Дано: GTIN товара не совпадает с GTIN в коде. Тогда: `GTIN_MISMATCH`. **3.** Дано: код неизвестен реестру ЦРПТ. Тогда: `MOCK_INVALID` с причиной мока. **4.** Каждая отклонённая попытка появляется в «Расхождениях» и в истории кода |

| UC | UC1, исключения А1, А2 |
| Экран / API | Операция (блок «Результат»: решение, код причины, сообщение); `POST /api/operations` |
| Реализуемость | Реализовано: 17 стабильных кодов причин (`SPEC.md` §1.5), ровно одна причина на попытку — первая не пройденная проверка. Пакетного отклонения «по каждому коду партии» в форме нет — см. US-23 |
