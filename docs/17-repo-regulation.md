## 2. Модель веток

Используется trunk-based модель: короткие ветки от `main`, слияние через pull request.

| Ветка | Назначение | Пример |
|---|---|---|
| `main` | Всегда собирается и проходит тесты; с неё ставятся теги релизов | — |
| `feat/<область>-<кратко>` | Новая функция | `feat/import-snapshot-check` |
| `fix/<область>-<кратко>` | Исправление ошибки | `fix/web-kpi-tile-color` |
| `docs/<кратко>` | Документация | `docs/risk-matrix` |
| `refactor/…`, `chore/…`, `test/…` | Рефакторинг, инфраструктура, тесты | `chore/ci-gitverse` |

Правила:

1. Прямой push в `main` запрещён: настройка защиты ветки в GitVerse — [проверить доступность защиты ветки в GitVerse].
2. Ветка живёт не дольше недели. Перед PR ветка обновляется от `main` через `git rebase origin/main`.
3. Конфликты решает автор PR у себя локально, затем повторно запускает `make test`. Конфликт в `SPEC.md` решается вместе со вторым владельцем контракта.
4. Слияние — squash merge: в `main` попадает один коммит на PR с заголовком PR в формате Conventional Commits.
5. Релиз: тимлид ставит аннотированный тег `vX.Y` на `main` после зелёного CI и `make verify`.

## 3. Коммиты

Формат — Conventional Commits, на английском, в повелительном наклонении, заголовок не длиннее 72 символов.

```
<type>(<scope>): <subject>

<body: why, not what — optional>
```

| type | Когда | Пример |
|---|---|---|
| `feat` | Новая функция | `feat(importer): add snapshot mismatch check` |
| `fix` | Исправление | `fix(ops): reject sell with reversed timestamp` |
| `docs` | Документация | `docs: add risk matrix and WBS` |
| `refactor` | Без изменения поведения | `refactor(reports): share filter builder` |
| `test` | Только тесты | `test(rules): cover GTIN-13 normalisation` |
| `chore` | Сборка, CI, зависимости | `chore(ci): add GitVerse workflow` |

`scope` — папка или пакет: `backend`, `ops`, `importer`, `reports`, `rules`, `mock`, `gen`, `web`, `ci`, `docs`.

## 4. Pull request и ревью

| Шаг | Кто | Что делает |
|---|---|---|
| 1 | Автор | Открывает PR в `main`. В описании: что сделано, ссылка на issue или ID требования (M1…, S1…), как проверить, скриншот для изменений UI |
| 2 | CI | Прогоняет пайплайн из раздела 6. Красный CI блокирует слияние |
| 3 | Ревьюер | Проверяет по чек-листу ниже, оставляет комментарии или одобряет. Срок — 2 рабочих дня |
| 4 | Автор | Исправляет замечания новыми коммитами в ту же ветку |
| 5 | Автор | После одобрения и зелёного CI делает squash merge и удаляет ветку |

Кто ревьюирует (по уставу — другая роль):

| Изменение | Ревьюер |
|---|---|
| `backend/`, `mock/`, `tools/gen/` | Жраков А.; правила проверок — также Завгороднев Я. |
| `web/` | Брусникин М. |
| `docs/` аналитика | Шиншин А. |
| `docs/` управление | Завгороднев Я. |
| `SPEC.md`, `data/`, `golden/` | Завгороднев Я. и Шиншин А. |

Чек-лист ревьюера:

- изменение соответствует `SPEC.md` или PR содержит правку `SPEC.md`;
- коды причин и порядок проверок не изменились без изменения версии правил `rules_version`;
- для новой логики есть тест; для изменения генератора обновлены `data/` и `golden/`;
- нет секретов, отладочного вывода и закомментированного кода;
- комментарии и идентификаторы в коде — на английском, тексты интерфейса и документы — на русском.

## 5. Критерии готовности (Definition of Done)

Задача считается выполненной, когда:

1. Код слит в `main` через PR с одобрением ревьюера другой роли.
2. CI зелёный; до проверки CI на GitVerse — локально пройден `make test`.
3. Для изменений правил, импорта или отчётов локально пройден `make verify`: K5 = 100%, K3 = 0.
4. Требование из MoSCoW проходит свой критерий приёмки из [MoSCoW](03-moscow.md).
5. Обновлены `README.md`, `SPEC.md` или документ в `docs/`, если изменилось поведение, API или модель данных.
6. Для изменений UI — экран проверен под ролью, которой он доступен, и под аудитором (только чтение).

## 6. CI

Файл: `.gitverse/workflows/ci.yaml`. Синтаксис совместим с GitHub Actions, который использует GitVerse CI/CD. Пайплайн повторяет `make test` без Docker внутри Docker: PostgreSQL для тестов backend поднимается как service-контейнер.

| Событие | Ветки |
|---|---|
| `push` | `main` |
| `pull_request` | в `main` |

| Job | Шаги | Что проверяет |
|---|---|---|
| `gen` | `go vet`, `go test`, `go run . -seed 16 -out ../../`, `git diff --exit-code -- data golden` | Генератор и независимый чекер; что закоммиченные T1 и эталоны воспроизводятся побайтно |
| `mock` | `go vet`, `go test` | Мок `/cz/verify` и режимы сбоев |
| `backend` | service `postgres:16-alpine`, `TEST_DATABASE_URL`, `go vet`, `go test`, `go build ./cmd/server` | Правила, движок операций, импорт, отчёты, API, сверку T1 с golden на настоящем PostgreSQL |
| `web` | Node 22, `npm ci`, `npm run build` (`tsc --noEmit` и `vite build`) | Типы TypeScript и сборку SPA |

Job запускаются параллельно. Версия Go берётся из `go.mod` каждого модуля (1.23). Без переменной `TEST_DATABASE_URL` интеграционные тесты backend пропускаются (`internal/testdb`), поэтому в CI она задана явно.

**Ограничение.** Пайплайн не запускался на раннерах GitVerse. Не проверено: наличие метки раннера `ubuntu-latest`, поддержка service-контейнеров и действий `actions/checkout@v4`, `actions/setup-go@v5`, `actions/setup-node@v4`. Локально 16.11.2026 проходят `go vet` и `go test` для `tools/gen` и `mock` и `go vet` для `backend`. Пока CI не подтверждён, обязательной проверкой перед PR остаётся `make test` (риск R15 в [матрице рисков](16-risk-matrix.md)).

Что CI не делает: не поднимает весь стек и не запускает `make verify` и `make demo` — им нужен Docker Compose. Эти проверки выполняет автор PR локально (критерий готовности 3) и тимлид перед тегом релиза.
