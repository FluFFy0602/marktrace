# 24. Нормализация до 3НФ и описание БД

**MarkTrace · версия 1.0 · 16.11.2026**

Документ закрывает практики 20–22: модель доводится до 3НФ, по каждому шагу дано обоснование, приведено описание структуры БД и план защиты модели данных. Объект — физическая схема `backend/internal/store/migrations/001_init.sql`, которая описана в [ERD](12-erd.md) и [словаре данных](13-data-dictionary.md).

## 1. Исходная точка: плоская выгрузка

Кейс 16 задаёт три файла: `items(item_code, name, gtin)`, `codes(code, item_code, status, ts)` и `operations(op_id, code, op_type, ts, actor)`. Учётная система обычно отдаёт журнал одной таблицей, где у каждой операции повторены данные товара и кода. Нормализацию показываем на такой ненормализованной таблице `ЖУРНАЛ`:

| op_id | code | item_code | name | gtin | op_type | ts | actor | status | коды партии |
|---|---|---|---|---|---|---|---|---|---|
| OP-1 | 0104…21AAAAAA | ITM-0001 | Йогурт 2%, 270 г | 04663468696923 | issue | 2026-09-01T08:03:33+03:00 | op-prod-01 | issued | 0104…21AAAAAA, 0104…21BBBBBB |
| OP-7 | 0104…21AAAAAA | ITM-0001 | Йогурт 2%, 270 г | 04663468696923 | introduce | 2026-09-02T10:00:00+03:00 | op-prod-01 | introduced | — |

Аномалии такой таблицы:

- **Вставка.** Нельзя завести товар без операции. Нельзя помнить ожидаемую привязку кода до `issue`.
- **Обновление.** Наименование товара повторяется в каждой операции его кодов, и исправление надо вносить в сотни строк.
- **Удаление.** Если удалить последнюю операцию кода, вместе с ней пропадёт привязка кода к товару.

## 2. Шаги нормализации

### 2.1. 1НФ: атомарные значения, нет повторяющихся групп

| До | После | Обоснование |
|---|---|---|
| «коды партии» — список кодов в одной ячейке | Строка на каждый код; операция партии = набор операций по одному коду | Каждое значение атомарно; проверки маски и перехода выполняются по отдельному коду |
| `ts` как строка в разных форматах и зонах | `timestamptz`: один момент UTC | Значение атомарно и сравнимо; `+03:00` и `Z` дают один момент |
| Код маркировки как составная строка `01`+GTIN+`21`+серия | Хранится одной строкой `code` | Код — идентификатор, составные части отдельно не используются. GTIN внутри кода извлекается правилом маски только для проверки `GTIN_MISMATCH` |
| Строка без ключа (повтор строки возможен) | PK `op_id`, альтернативный ключ `(code, ts)` | Повтор распознаётся по ключу: дубль или `IDEMPOTENCY_CONFLICT` |

### 2.2. 2НФ: нет зависимостей от части ключа

В `ЖУРНАЛ` после 1НФ есть два потенциальных ключа: `op_id` и `(code, ts)`. Относительно составного ключа `(code, ts)`:

- `item_code`, `name`, `gtin` зависят только от `code` — от части ключа;
- `op_type`, `actor`, `op_id` зависят от всего ключа.

| До | После | Обоснование |
|---|---|---|
| `ЖУРНАЛ(op_id, code, ts, op_type, actor, item_code, name, gtin, status)` | `operations(op_id, code, op_type, ts, actor)` + `КОД(code, item_code, name, gtin)` | `code → item_code` — зависимость от части ключа `(code, ts)`; привязка уходит в отдельную таблицу |

### 2.3. 3НФ: нет транзитивных зависимостей

| До | После | Обоснование |
|---|---|---|
| `КОД(code, item_code, name, gtin)` | `code_registry(code, item_code, expected_status, expected_ts)` + `items(item_code, name, gtin)` | `code → item_code → name, gtin` — транзитивная зависимость; товар выносится в `items` |
| `status` в каждой строке журнала | Статус не хранится в `operations`; текущий статус — в `codes` | `status` после операции выводится из `op_type` (`op_type → status`) — транзитивная зависимость через неключевой атрибут |
| Ожидаемый статус из `codes.csv` и фактический статус в одной таблице | `code_registry.expected_*` (ожидание) и `codes.status/ts` (факт) | Это разные факты с разными источниками; при совмещении нельзя обнаружить `SNAPSHOT_MISMATCH` |

Итог — схема из [ERD](12-erd.md). Отказы, протокол импорта и разбор вынесены в отдельные таблицы, а не в столбцы-флаги предметных таблиц. Поэтому отклонённый ввод не попадает в `items`, `code_registry` и `operations` и не нарушает их ключи.

## 3. Проверка каждой таблицы

ФЗ — функциональные зависимости, PK — первичный ключ, AK — альтернативный ключ.

| Таблица | Ключи | Основные ФЗ | 1НФ | 2НФ | 3НФ | Замечание |
|---|---|---|---|---|---|---|
| `users` | PK `username` | `username → password_hash, role, display_name` | да | да (ключ простой) | да | `display_name` задаётся на учётную запись, а не выводится из роли |
| `sessions` | PK `token` | `token → username, expires_at` | да | да | да | — |
| `items` | PK `item_code` | `item_code → name, gtin` | да | да | да | `gtin` не ключ: два товара с одним GTIN допустимы |
| `code_registry` | PK `code` | `code → item_code, expected_status, expected_ts` | да | да | да | `name`, `gtin` товара не дублируются |
| `codes` | PK `code` | `code → status, ts, last_actor`; `code → item_code` | да | да | **нет — намеренно** | `item_code` транзитивно выводится через `code_registry`; `status, ts, last_actor` выводятся из `operations` (раздел 4) |
| `operations` | PK `op_id`; AK `(code, ts)` | `op_id → code, op_type, ts, actor, attempt_id, created_at`; `(code, ts) → op_id` | да | да | да | Оба ключа определяют все атрибуты. Статус не хранится |
| `import_sessions` | PK `session_id` | `session_id → started_by, role, started_at, finished_at, status, failure_reason, files, counters, rows_created` | **с оговоркой** | да | **с оговоркой** | `files`, `counters` — JSON; `counters` выводим из `import_rows` (раздел 4) |
| `import_rows` | PK `row_id` | `row_id → session_id, entity, line_no, key, raw, processing_status, reason` | **с оговоркой** | да | да | `raw` — JSON-массив; `key` = `raw[0]` (раздел 4) |
| `operation_attempts` | PK `attempt_id` | `attempt_id → source, import_row_id, op_id, code, op_type, ts_raw, actor, initiator, role, decision, reason, mock_result, rules_version, created_at` | да | да | **с оговоркой** | У импорта сырые поля повторяют `import_rows.raw` (раздел 4) |
| `violations` | PK `violation_id` | `violation_id → source, ref, code, item_code, reason, message, attempt_id, import_row_id, rules_version, created_at, op_ts, actor` | да | да | **с оговоркой** | `code, item_code, op_ts, actor` повторяют источник (раздел 4) |
| `violation_resolutions` | PK `id`; частичный AK `(violation_id) WHERE action='close'` | `id → violation_id, action, comment, author, created_at` | да | да | да | Состояние нарушения не хранится, а выводится из наличия `close` |

Ни в одной таблице нет составного первичного ключа, поэтому зависимостей от части PK не бывает. Для `operations` с AK `(code, ts)` все неключевые атрибуты зависят от пары целиком. 2НФ выполняется везде.

## 4. Намеренная денормализация

Каждое отступление от 3НФ сделано осознанно: известен источник истины, и есть способ проверить согласованность.

| Где | Что избыточно | Зачем | Источник истины и контроль |
|---|---|---|---|
| `codes.status`, `codes.ts`, `codes.last_actor` | Выводятся из последней по `ts` строки `operations` кода | Отчёт «Коды» с фильтрами и счётчиками — один запрос к одной таблице с индексами (K4 ≤ 2 с) | `operations`. Проекция обновляется в той же транзакции, что и вставка операции, под блокировкой кода. K2 пересчитывает статус по `operations` и сравнивает: после T1 — 100% |
| `codes.item_code` | Копия `code_registry.item_code` | Фильтр по товару без соединения таблиц | `code_registry`. Привязка неизменна, копия пишется один раз при `issue` |
| `import_rows.raw` (jsonb-массив) | Не атомарен в строгом смысле 1НФ | Сохранить вход как есть, включая лишние или недостающие поля, неверный формат и пустые значения. Разбить такую строку на типизированные столбцы нельзя | Сам вход. Поэлементно читается только `raw->>1` (товар строки `codes.csv`) при повторной проверке `ITEM_NOT_FOUND` |
| `import_rows.key` | Равен первому элементу `raw` | Индекс `(entity, key)` для поиска прежних отказов той же строки (идемпотентность K3) | `raw` |
| `import_sessions.counters` | Выводимы группировкой `import_rows` по `entity, processing_status` | Протокол и список сеансов без агрегатов по тысячам строк | `import_rows`. Пишутся один раз при закрытии сеанса |
| `import_sessions.rows_created` | Частично выводимо: не все новые строки ссылаются на сеанс (у `SNAPSHOT_MISMATCH` нет ссылки) | K3 — число новых строк в сеансе повторного импорта | Значение фиксируется при закрытии сеанса и далее не пересчитывается |
| `import_sessions.files` (jsonb-массив) | Повторяющаяся группа `{entity, filename, size, sha256}` | Метаданные читаются целиком. По `sha256` K3 узнаёт повторный импорт того же набора | Загруженные файлы; не меняется |
| `operation_attempts.op_id, code, op_type, ts_raw, actor` при `source='import'` | Повторяют элементы `import_rows.raw` | Одна структура для попыток формы и импорта: K1 и лента попыток считаются по одной таблице | `import_rows.raw` для импорта, тело запроса — для формы |
| `operation_attempts.mock_result` (jsonb) | Ответ внешней системы целиком | Ответ мока сохраняется без потерь, включая неожиданные поля и синтезированный отказ | Ответ мока; не меняется |
| `violations.code, item_code, op_ts, actor` | Повторяют данные строки или попытки | Фильтры «Расхождений» по коду, товару, исполнителю и периоду без соединений. У нарушений `items`/`codes` и `SNAPSHOT_MISMATCH` нет попытки, у формы нет строки | Вход на момент проверки. `item_code` в нарушении — значение из входа и может расходиться с реестром (например, при `DUPLICATE_CODE`), поэтому это не транзитивная зависимость от `code` |
| `violations.message` | Строится из `reason` и подробности | Текст сообщения фиксируется на момент проверки и не меняется при правке каталога сообщений | Не пересчитывается |

Обратная сторона денормализации — риск рассинхронизации. Его снижают три меры: в БД пишет только backend, проекция обновляется в транзакции операции, а записи журналов неизменяемы. UPDATE в коде выполняется только в трёх местах: upsert проекции `codes`, итог строки `import_rows` внутри её же транзакции и закрытие сеанса `import_sessions`.

## 5. Описание структуры БД

### 5.1. Сводка

| Показатель | Значение |
|---|---|
| СУБД | PostgreSQL 16; схема создаётся миграцией `001_init.sql` при старте backend |
| Таблиц | 11 предметных и служебных + `schema_migrations` |
| Первичных ключей | 11 (5 естественных `text`, 6 суррогатных `uuid`) |
| Внешних ключей (FK) | 7: `sessions → users`, `code_registry → items`, `codes → code_registry`, `operations → code_registry`, `import_rows → import_sessions`, `operation_attempts → import_rows`, `violation_resolutions → violations` |
| Логических ссылок без FK | 3 на ERD (`operations.attempt_id`, `violations.attempt_id`, `violations.import_row_id`) и ссылки на `users` из `started_by`, `initiator`, `author` |
| Ограничений UNIQUE | 2: `operations(code, ts)` и частичный уникальный индекс одного `close` |
| Ограничений CHECK | 10 (перечисления и непустой комментарий) |
| Неуникальных индексов | 10 |
| Типы связей | 1:N по FK — R1, R2, R4, R5, R6, R7; 1:0..1 — R3 по FK и R8–R10 логические; M:N — нет |

### 5.2. Логика структуры

1. **Справочник и привязка.** `items` → `code_registry`. Код известен системе, как только принята строка `codes.csv` или форма приняла `issue` с товаром.
2. **История и состояние.** `operations` хранит только принятые события. `codes` — текущее состояние для отчётов. Пара `(code, ts)` уникальна, поэтому история кода упорядочена однозначно.
3. **Каждая попытка оставляет след.** Строка CSV → `import_rows`. Попытка операции → `operation_attempts`. Отказ → `violations` ровно с одной причиной. Дубль ничего не добавляет в предметные таблицы.
4. **Разбор отдельно от факта.** `violation_resolutions` дополняет нарушение комментариями и закрытием, но не меняет его.
5. **Доступ.** `users` и `sessions` дают роль; роль проверяется до записи.

Описание каждой таблицы и столбца — в [13-data-dictionary.md](13-data-dictionary.md); связи, ограничения и транзакции — в [12-erd.md](12-erd.md).

### 5.3. Выбор типов

| Решение | Почему |
|---|---|
| Естественные ключи `text` для `items`, `code_registry`, `codes`, `operations` | Ключи приходят из учётной системы и CSV, по ним работает идемпотентность; суррогат дал бы второй ключ без пользы |
| `uuid` для журналов | Записи журналов создаёт система; ключ генерируется без обращения к БД и не повторяется между сеансами |
| `text` без длины | В PostgreSQL `text` и `varchar(n)` хранятся одинаково. Формат значений проверяется правилами (24 символа кода, 13/14 цифр GTIN) с понятной причиной отказа, а не ошибкой БД |
| GTIN как `text` | Ведущий ноль значим; GTIN — идентификатор, а не число |
| `timestamptz` | Хранит момент UTC: операции с разными смещениями сравнимы |
| `jsonb` для сырого входа и метаданных | Структура входа может быть неверной; JSON сохраняет её без потерь |

### 5.4. Что можно усилить следующей миграцией

Не реализовано, это предложения для `002_*.sql`:

- CHECK на `operations.op_type` и `code_registry.expected_status`. Сейчас значения проверяются только кодом;
- FK `codes.item_code → items`, `operations.attempt_id → operation_attempts`, `violations.attempt_id → operation_attempts`, `violations.import_row_id → import_rows`;
- UNIQUE на непустой `operation_attempts.import_row_id`, чтобы связь R6 стала 0..1 и на уровне БД.
