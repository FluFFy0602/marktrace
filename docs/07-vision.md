# 07. Vision продукта

## Пресс-релиз из будущего (метод занятия 1.10)

> **MarkTrace: ошибки маркировки находят до проверки, а не после.** Через год после запуска макета компании, которые готовятся к работе с «Честным знаком», проверили свои процессы и данные без УКЭП и риска для боевых систем. Контролёр качества за минуты видит, какой код в каком статусе, какая операция нарушила порядок и кто её провёл. Доля корректно оформленных операций на наборе из 500 кодов достигла 99%.

## Vision Statement

**Для** контролёров качества данных и операторов склада, производства и розницы, работающих с маркируемым товаром,
**которые** тратят часы на ручной разбор расхождений между журналом операций и статусами кодов,
**наш продукт** MarkTrace
**является** макетом системы учёта жизненного цикла кодов маркировки,
**который** автоматически проверяет формат кода и GTIN, порядок операций и уникальность кодов и показывает статусы и расхождения с причиной отклонения,
**в отличие от** личного кабинета оператора, облачных сервисов маркировки и ручного учёта в Excel,
**наш продукт** даёт безопасный стенд с открытыми правилами, эталонными наборами и идемпотентным импортом, без УКЭП и без подключения к боевым системам.

Слоган: **«Каждый код — на своём месте жизненного цикла».**

## 1. Проблема

Операции с кодами оформляют в неправильном порядке, форматы кодов и GTIN содержат ошибки, статус кода расходится с журналом, а расхождения разбирают вручную.

## 2. Целевая аудитория

| Сегмент | Описание | Роль в MVP |
|---|---|---|
| Контролёр качества данных | Аудит расхождений, повторный импорт исправленных данных | **Основной** |
| Оператор розницы/склада | sell / return / dispose | Основной |
| Оператор производства | issue / introduce | Второй |
| Аудитор | Только чтение | Второй |

## 3. Ценностное предложение

1. Понятная причина каждого отклонения (какое правило нарушено).
2. Один источник истины: статус считается из последней валидной операции.
3. Безопасный повтор импорта: дубли не создаются.
4. Работа без УКЭП и боевых данных: подходит для обучения и отладки процесса.

## 4. Границы системы

| Входит | Не входит |
|---|---|
| Операции issue / introduce / sell / return / dispose с проверкой переходов | Боевая интеграция с ЦРПТ / ГИС МТ |
| Проверка формата кода, GTIN, уникальности, времени | УКЭП и юридически значимые документы |
| Отчёты «Статусы» и «Расхождения», сводка KPI, экспорт CSV | Агрегация (короба, паллеты), печать DataMatrix |
| Импорт CSV с журналом сессий и идемпотентностью | ЭДО, УПД, расчёты с контрагентами |
| REST-мок `POST /cz/verify` | Персональные данные, мобильное приложение, прод-деплой |

## 5. Метрики успеха

| Метрика | Цель |
|---|---|
| Доля корректно оформленных операций на макете | ≥ 99% |
| Новых строк при повторном импорте того же файла | 0 |
| Совпадение отчётов с эталоном `golden/*` | 100% |
| Время построения отчёта по статусам на T1 | ≤ 2 с |

## 6. Ограничения и допущения

- Только синтетические данные; маска кода учебная, зафиксирована в `SPEC.md` §1.2 (допущение Д1).
- GTIN-14 основной, GTIN-13 допустим с оговоркой в README.
- Технологии: Go и PostgreSQL на сервере, React и TypeScript в браузере, REST-мок, Docker Compose, Git.
- Срок 8 недель, команда 4 человека.

## Проверка по инсайтам рынка

| Инсайт ([матрица конкурентов](05-competitor-matrix.md)) | Где учтён |
|---|---|
| Причина ошибки неясна | Ценность 1, метрика совпадения с эталоном |

## Критика («злой скептик») и ответы

| Вопрос | Ответ |
|---|---|
| Зачем макет, если есть реальные сервисы? | Реальные сервисы требуют УКЭП и боевых данных; макет отрабатывает правила и проверки без риска и объясняет ошибки |
| Маска кода условная — какая от неё польза? | Правила переходов и целостности не зависят от маски; маска версионируется и заменяется |
| Почему 99%? | Цель задана кейсом; в T1 заложены ошибочные строки, сверка идёт с эталоном |
