## 2. Обоснование (бизнес-требования)

Участники оборота маркируемых товаров обязаны вести учёт кодов по жизненному циклу. Ошибки в последовательности операций, формате кода и GTIN ведут к расхождениям с данными оператора и к штрафам. Нужен безопасный способ отработать процесс и проверки данных до подключения к боевым системам.

## 3. Цели и критерии успеха

| Цель | Критерий |
|---|---|
| Смоделировать жизненный цикл кода: выпуск → ввод → реализация → возврат → вывод | BPMN и диаграмма состояний утверждены заказчиком |
| Автоматизировать проверки атрибутов и переходов | Все нарушения из набора T1 найдены, совпадение с `golden/violations.csv` |
| Дать отчётность по статусам и расхождениям | Отчёты с фильтрами и экспортом CSV; построение ≤ 2 с на T1 |
| Подтвердить качество данных | Доля корректных операций ≥ 99% |

## 4. Объём работ

**В объёме:** формы операций, реестр кодов (`code_registry` и проекция `codes`; в 1С — регистр сведений «мт_СтатусыКодов», см. [29](29-1c-target.md) §7), отчёты «Статусы» и «Расхождения», сводка KPI, импорт/экспорт CSV с журналом, мок `POST /cz/verify`, UI трекинга кода, BPMN, ERD, словарь данных, набор T1 (T2 — Could C2, не сделан), README, ТЗ ([30-tz.md](30-tz.md)), презентации к защитам, видео 3–5 мин.

**Вне объёма:** боевая интеграция с ЦРПТ/ГИС МТ, УКЭП, агрегация, печать кодов, ЭДО, персональные данные, прод-деплой.

Состав и RACI — в [карточке проекта](01-project-card.md). Тимлид (Шиншин Алексей) согласует MoSCoW вместе с аналитиком (Завгороднев Ярослав) и заказчиком. Изменения объёма — только через issue `scope-change` с оценкой влияния. Каждый PR получает ревью от другой роли.

## 8. Ограничения

- Реальной интеграции с «Честным знаком» нет, только REST-мок.
- Только синтетические или обезличенные данные, без ПДн.
- Технологии: Go и PostgreSQL на сервере, React и TypeScript в браузере, REST-мок, Docker Compose, Git (GitVerse или эквивалент).
- Объём MVP: не более 5 пользовательских операций (форма ввода + отчёты).
- Ресурс — ≈ 192 чел.-ч (4 человека × 6 ч × 8 нед).
- 1С-контур (демо-база, лицензии) команде не предоставлен: MVP сделан на Go, PostgreSQL и React, целевой контур 1С описан в [29-1c-target.md](29-1c-target.md) (риски R01, R02).

## 12. Критерии приёмки проекта

1. Модель процесса показывает корректные переходы статусов.
2. Реализованы проверки GTIN, уникальности и последовательности.
3. Отчёт экспортируется в CSV (`code, item_code, status, last_ts`).
4. Приложены README и контрольные примеры; результаты совпадают с эталоном T1.
5. Выполнено ≥ 80% критериев приёмки ТЗ ([30-tz.md](30-tz.md) §10).
